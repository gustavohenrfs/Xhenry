# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

XHenry (formerly "Suzana", still the SQLite filename `data/suzana.db` and the owner email `local@suzana`) is a dashboard for monitoring X (Twitter) accounts grouped into folders: account health (search ban / ghost ban / suspended), post metrics (views, likes, retweets, replies, followers), best-time-to-post suggestions, Telegram alerts, and a Grok (xAI) "will this post get restricted?" reviewer. FastAPI + SQLAlchemy backend, single-page vanilla JS frontend. All user-facing strings, comments and docstrings are in Brazilian Portuguese — keep new ones in Portuguese.

## Commands

```bash
python -m pip install -r requirements.txt
copy .env.example .env
python -m uvicorn main:app --host 127.0.0.1 --port 8000   # add --reload for dev
```

Tests: `python -m pip install -r requirements-dev.txt` then `python -m pytest -q` (Cloaker, auth/route protection, password reset, session revocation, collectors, dashboard, health check, archiving, Telegram, the watchdog and robo.py: `tests/test_robo.py` covers the proxy relay against fake local proxies plus pure rules, `tests/test_robo_e2e.py` runs whole rounds with a fake `anyx` against a throwaway Postgres given by `ROBO_TEST_DATABASE_URL` (skipped otherwise; it drops all tables); `tests/conftest.py` points `DATABASE_URL` at a throwaway SQLite and sets `WATCHDOG=off` before importing `app.*`; the X API and Telegram are monkeypatched, never called). No linter. The only build step is the Tailwind CSS (`sh scripts/build_css.sh`, output committed; see Frontend). On Python 3.15 `uvicorn[standard]` fails to build `pyyaml` without MSVC; install plain `uvicorn` locally. OpenAPI docs at `/docs` unless `APP_ENV=production`.

## Configuration

`.env` is loaded by a hand-rolled parser in `app/database.py` (`load_env_file`, uses `setdefault`, so real env vars win). Key vars:
- `DATABASE_URL` — Postgres in production (Render/VPS); `postgres://`/`postgresql://` are rewritten to `postgresql+psycopg://`. Unset → SQLite at `data/suzana.db`.
- `X_BEARER_TOKEN` — needed only for `/api/check*`; without it the dashboard still loads and checks return 503.
- `SECRET_KEY` — required for `/api/login` (HMAC-signed tokens).
- `ALLOW_REGISTRATION` — `/api/register` returns 403 unless this is `true` (missing = closed). Turn it on only to create an account.
- `TELEGRAM_BOT_TOKEN` (or `TELEGRAM_TOKEN`, the name robo.py uses) / `TELEGRAM_CHAT_ID` — the only Telegram source (`telegram_creds` ignores the legacy `app_settings.telegram_*` columns; one bot for panel, robot and backup). There are no Telegram fields in the UI any more.
- `XAI_API_KEY`, `XAI_MODEL` — fallbacks; the `app_settings` row (id=1, edited via `/api/settings`) takes precedence.
- `PUBLIC_URL` — base of the password-reset link sent to Telegram (falls back to the request URL, which is wrong behind nginx).

## Architecture

- `main.py` — app factory. Lifespan runs `Base.metadata.create_all`, then `ensure_user_auth_columns()` and `ensure_owner()`. **There is no migration tool**: new columns on existing tables must be added by hand via `ALTER TABLE` (add them to `ensure_user_auth_columns` in `app/services.py`, which runs at startup). `create_all` will not alter existing tables, and won't add a new `Index` to one either: add it to the model and to the `indexes` dict in `ensure_user_auth_columns` (`CREATE INDEX IF NOT EXISTS`).
- `app/models.py` — all tables (`users`, `folders`, `x_accounts`, `health_checks`, `daily_metrics`, `folder_daily_metrics`, `tweet_samples`, `sync_runs`, `app_settings`, `alerts_sent`, `day_baselines`, `collectors`, `push_subscriptions`). `import app.models` in `main.py` is what registers them on the metadata.
- `app/services.py` — nearly all business logic; routers are thin. Key flows:
  - **Health check** (`check_handle` → `collect_health` → `derive_status` → `persist_account`): calls X API v2 (user lookup, user timeline, recent search) and maps HTTP statuses to a `HealthStatus`. Writes a `HealthCheck`, a profile snapshot into `DailyMetric`, a `SyncRun`, rebuilds the `FolderDailyMetric` rollup, then sends a Telegram ban alert on status transition (deduped via `alerts_sent.dedupe_key`).
  - **Dashboard** (`dashboard`, `account_payload`, `build_suggestions`): reads only the DB (`tweet_samples`, `daily_metrics`). It never calls the X API. Performance: `load_samples` reads the posts once (only `SAMPLE_COLUMNS`, light rows instead of ORM objects) from the oldest day any card needs (`since`: previous window or the 14-day line), each window is then an in-memory filter (`within`); `latest_metrics`, `last_check_details`, `followers_gained` and the folder counts are one query each for all accounts (no per-account queries); best times only load the whole history when the period has fewer than 3 posts. For `total`, the charts (`growth`, `spark`, `series`) start at the first post (at least 14 days), not 10 years back; the KPIs still use the full window. `GET /api/dashboard` goes through `app/cache.py` (in-memory, per period and folder, stored as JSON bytes with an ETag; an `If-None-Match` hit returns 304): an entry is valid while the "data version" is the same (a counter bumped after every non-GET `/api/` request by the `ForgetOnWrite` middleware, plus `max(collected_at)` of `tweet_samples`/`daily_metrics`, which robo.py sets to `NOW()` on every write, plus `max(sync_runs.id)`) and for at most 60 s ("today" depends on the hour). Single uvicorn process only, like the Cloaker. A direct DB write that touches none of those (e.g. a manual SQL update) shows up within 60 s. Cards: Views (with a sparkline of `spark`, the last 14 days for short periods), views per post, followers gained (`followers_gained`: last reading up to the end minus the last one before the start), Curtidas, Retweets, Replies, Citações, Salvamentos (`None` when the period sums 0, since older robo.py runs always wrote 0), an Interações donut with `interaction_rate` (likes+RTs+replies+quotes+bookmarks ÷ views, in %; deliberately not named "engagement"), and the top post with its x.com link. The "Potencial de Crescimento" chart uses `growth` (`growth_payload`): for a single day, views cumulated by posting hour (cut at the current hour today) against the previous day, plus `pace` (today up to now vs yesterday up to the same hour); for longer periods, views per day with the previous window aligned day by day; posts as bars in both. Also: `top_posts` (top 10 of the period, `top_post` is the first), `goal` (`app_settings.impression_goal` repurposed as the daily views goal, Configurações → "Meta de views do dia"; `today` is always today's views), `suggestions.heatmap` (7×24 average views by weekday/posting hour, `None` where nothing was posted), and per account card `spark` (14 days) and `views_prev`. "Alertas recentes" reads `GET /api/alerts` (login), the latest `alerts_sent` rows. The header bell reads `GET /api/viral` (login): only `kind=viral` rows, resolved by `services.viral_item` through robo.py's key `viral:{account_id}:{tweet_id}[:{level}]` to the level (`VIRAL_LEVELS`: viralizando, bombando, 100k, 1m), the account, the x.com link and the current views (falls back to parsing the alert text when the account is gone). app.js polls it every 60 s on any tab; ids above `localStorage.viral_seen_id` make the badge. Clicking the bell asks for notification permission and subscribes the browser to **Web Push** (`app/push.py`, `app/routers/push.py`: `/api/push/key|subscribe|unsubscribe|test`, all login; the VAPID key is generated on first use into `app_settings.vapid_private_key`, `VAPID_PRIVATE_KEY` in `.env` wins; needs `pywebpush`). The watchdog then pushes every new viral alert to every subscription (cursor `app_settings.push_last_alert_id`, set to the newest id on the first run or while nobody is subscribed, so history never floods; at most `MAX_PER_TICK` 5 per minute, the rest goes on the next minute; alerts older than the 6 h TTL are skipped) and deletes subscriptions answered with 404/410. Any panel load with permission granted re-subscribes (upsert), and so does "Testar". `static/sw.js` is served at `/sw.js` (root scope), shows the notification with the logo (`requireInteraction`, so it stays on screen on Windows) and caches nothing; on `pushsubscriptionchange` it re-subscribes with the old key and calls the public `POST /api/push/renew`, which only replaces an existing row matched by `old_endpoint` (the old push URL is the proof; the SW can't see the login token). Without push (plain HTTP, old browser) the open tab notifies by itself for ids above `viral_notified_id`. "Testar" in the bell sends `/api/push/test` to this browser only. The app is installable (`/manifest.webmanifest`, icons in `static/img/`, "Instalar" button from `beforeinstallprompt`, instructions on iPhone where push only works installed). Each comes with a delta against `previous`, the same-size window before (`COMPARE_LABELS`; `total` has none). The "Saúde da coleta" card reads `GET /api/robo/health` (login; counts only, never proxy/cookies): accounts whose `collected_at` is older than `max(60, 2 * ceil(accounts/free collectors) * interval)` min, and free/benched/off collectors. Best-time suggestions rank hours by average `view_count`. The `engagement_count`/`engagement_rate` columns are legacy: kept on the tables so `robo.py` inserts don't break, but nothing in the app reads or writes them.
  - Tweet metrics are **not collected by this app** — they are written into `tweet_samples`/`daily_metrics` by `robo.py` (repo root, run by cron on the VPS; the app only imports its `ProxyRelay` for the collector proxy probe). `upsert_tweet`/`recompute_days` exist here but aren't wired to any route.
- `app/watchdog.py` — background task started in `main.py`'s lifespan (off with `WATCHDOG=off`; `tests/conftest.py` sets it off). Every 60 s: pushes new viral alerts to subscribed browsers (`push_new_alerts`); sends "Robô parado" when the last robo heartbeat (`sync_runs` row with `kind=tweets`, `account_id` NULL, status ok/partial) is older than `ROBO_SILENCE_MIN` (15); stays quiet if no heartbeat ever existed. With `AUTO_CHECK_MINUTES` > 0 it runs `check_handle` on stale accounts, which is what fires the existing Ghost/Search Ban alert (`dispatch_alerts`); off by default because it spends X API quota.
- Robot control (`app/routers/robo.py`, Configurações → Robô): `app_settings.robo_enabled`, `robo_interval_min` (one of `ROBO_INTERVALS`) and `robo_run_requested_at` (columns added at startup). `POST /api/robo/run` is what "Atualizar Dados" calls; the button then polls `GET /api/robo` until the request is cleared and a heartbeat newer than it exists. Cron runs robo.py every minute; robo.py's `round_plan` clears a pending request and does a manual round (all accounts, collectors in rotation, up to 3 each), otherwise runs only when enabled and the last heartbeat is older than the interval. Turning collection back on sets a request. The watchdog stays quiet when disabled or while a request is under 5 min old, and its limit is `max(ROBO_SILENCE_MIN, 2*interval+5)`.
- `robo.py` (repo root, standalone: raw psycopg SQL, Postgres only, imports `anyx` lazily; cron every minute as a non-root user; reads the repo `.env` or `ROBO_ENV_FILE`; lock and offline-alert stamp in `ROBO_STATE_DIR`, default `~/.xhenry-robo`) writes `tweet_samples`/`daily_metrics`, one heartbeat per run in `sync_runs`, and sends views alerts by level (`VIEW_LEVELS`: >500 viralizando, >10k POST BOMBANDO, >100K, >1M; once per post and level, only the highest level reached is sent), views-drop (today vs yesterday, from 23h), collector and collection-error alerts, deduped via `alerts_sent`. It never logs into the monitored accounts: each run pairs every free collector with one monitored account (oldest `x_accounts.collected_at` first), opens anyx logged into the collector through a local relay to the collector's proxy (Chrome can't do proxy auth), reads, closes the browser. Followers at most hourly (`followers_at`). A 429 stops the run and pauses that collector (`collectors.paused_until`). `classify` maps errors to a pause (`PAUSE_FOR`): an error whose text has `account/access` or `__cf_chl` (Cloudflare "Verify you are human"; anyx reports it as `SessionExpired: is locked by X`) is `verificacao` (6 h, 🛡️ alert telling to solve it in a browser and press Testar), checked before `sessao` (24 h, cookies). Collector test requests (`pending_tests`/`run_tests`) run first in every cron minute, even with collection off and without a heartbeat: the collector reads the next account in the queue (a normal read: saves posts, can pause and alert) and the result goes to `collectors.test_status`/`test_detail`; a collector whose @ is monitored is never opened.
- Collectors (`app/collectors.py` pure parsing/masking, `app/routers/collectors.py`, Coletores tab): burner accounts with proxy and x.com cookies stored in plain text for the robot. Every `/api/collectors*` route needs login, and responses only carry masked values (`http://user:***@host:port`, `auth_token …abcd`); never add these columns to a public payload. A handle can't be both a collector and a monitored account (both create routes refuse; the robot also skips such collectors). "Testar" (`POST /api/collectors/{id}/test`) clears `paused_until`, probes the proxy right away with `app.collectors.probe_proxy` (robo.py's `ProxyRelay`: a CONNECT tunnel to x.com:443, no cookies, no page) and, if it works, sets `test_requested_at` for robo.py; the panel never opens a browser itself (anyx and its cookie vault belong to the robot's user). The tab polls `/api/collectors` every 30 s while open, every 5 s while a test is pending, and toasts the result. The app imports `robo` only for that probe.
- `app/cloaker.py` — pure module (no FastAPI) behind the Cloaker tab: `build_variants` makes N image/video variants with distinct sha256 (few-px crop + resize back, tone shift, ±1 noise, re-encode; metadata always stripped, optional fresh EXIF/creation_time). Image output format comes from the file content, not the declared type (`detect_image_ext`), and an embedded ICC profile is converted to sRGB before being dropped. Video uses the ffmpeg binary bundled by `imageio-ffmpeg`. `CloakerError` messages are user-facing Portuguese and become HTTP 400. Exposed by `app/routers/cloaker.py` (`POST /api/cloaker`, requires login, returns a zip + `X-Cloaker-Manifest` header). Video jobs stay on disk in a per-request dir under `data/tmp` (removed by a `BackgroundTask` after the response), run one at a time (`_VIDEO_SLOTS`, 429 when busy) and share a `VIDEO_JOB_BUDGET` of 1800 s; images are capped at 40 MP. Video limits ("Vídeo acima de 100 MB", up to 20 copies: `MAX_VIDEO_BYTES` 100 MB, `MAX_COPIES_VIDEO` 20) are duplicated as `CLOAKER_MAX_VIDEO_*` in app.js plus hint text in index.html — change all three together. On the VPS keep nginx `client_max_body_size` above the byte limit (110M) and `proxy_read_timeout` above the budget (1860s). Progress bar: the tab sends a random `job_id`, `build_variants(on_progress=...)` feeds an in-memory dict in the router, and the tab polls `GET /api/cloaker/progress/{job_id}` — this only works with a single uvicorn worker.
- `app/routers/` — `accounts.py` (folders, accounts, check, dashboard), `auth.py` (register/login/me, custom HS256 JWT + PBKDF2 hashing implemented by hand, no JWT/hash library), `checks.py` (settings, Telegram test, Grok post review), `pages.py` (serves `/`, `/health` and legacy `/avatars/{file}`).
- Auth (`current_user`, usually as `dependencies=[Depends(current_user)]` on the decorator) is enforced on every write or cost-incurring route: `/api/me*`, `/api/change-password`, `/api/settings` (GET/PUT), `/api/telegram/test`, `/api/posts/review`, folder/account POST/PATCH/DELETE, `/api/check*`, `/api/cloaker` (and its `/progress/{job_id}`), `/api/collectors*` (including GET), `/api/robo*` (including GET), `/api/alerts`, `/api/viral`, `/api/push/*`. Read-only routes stay public: `/sw.js`, `/manifest.webmanifest`, `/api/config`, `/api/dashboard`, `/api/suggestions`, `GET /api/folders`, `/api/refresh-all`; so are `/api/push/renew` (see above), `/api/login`, `/api/register` (gated by `ALLOW_REGISTRATION`) and `/api/password-reset/{request,confirm}`. `tests/test_auth_routes.py` pins this list — update it when adding routes. Logging in only gates access: folders, accounts and settings are not scoped per user, all data hangs off a single implicit owner (`local@suzana`), so any account that can log in can edit everything.
- Archiving accounts: `PATCH /api/accounts/{id}` with `is_archived` sets the flag and `archived_at` (column added at startup by `ensure_user_auth_columns`). Archived accounts are left out by `selected_accounts` (dashboard, KPIs, suggestions, `/api/check-all`), `accounts_for` (single check), the folder counts, the watchdog auto-check and `robo.py`'s account query; their rows in `tweet_samples`/`daily_metrics`/`health_checks` stay. `GET /api/accounts/archived` (public, read-only) returns them with all-time totals and the daily views/followers history for the Arquivadas tab.
- Password reset (`app/routers/auth.py`): "Esqueceu a senha?" posts the email to `/api/password-reset/request`, which sends `PUBLIC_URL/#reset=<token>` to the configured Telegram chat (same answer whether the email exists or not, 60 s in-memory cooldown per email). The token is signed with a key derived from `SECRET_KEY` (not interchangeable with login tokens), lasts 15 min and embeds a fingerprint of `senha_hash`, so it stops working once the password changes. No DB table. Login tokens carry `ver` = `users.token_version` (column added at startup); `current_user` rejects a mismatch, and both the reset and `/api/change-password` bump it, logging out every open session (change-password returns a fresh `access_token` so the current tab stays in). Tokens without `ver` (issued before this) count as 0.
- Dates/times: stored in UTC; SQLite returns naive datetimes, so wrap with `as_utc()` before converting. Day bucketing uses `America/Sao_Paulo` (`DEFAULT_TZ`). Periods: `today, yesterday, 7d, 30d, 3m, 1y, total`.

## Operations (VPS)

`scripts/backup.sh` is the daily backup (cron): `pg_dump -Fc` verified with `pg_restore --list`, a tar.gz of the legacy `data/avatars`, retention by `BACKUP_KEEP_DAYS` (14) in `BACKUP_DIR` (`/var/backups/xhenry`), and a Telegram message naming the failed step (token from env/.env only). It reads only the keys it needs from `.env` (never sources it). `.gitattributes` keeps `*.sh` LF.

## Frontend

`/` serves `templates/index.html` as a static `FileResponse` (no template engine, `no-cache` so it revalidates with a 304). **All frontend JS lives in `static/js/app.js`**, loaded with `defer` in `<head>` as `/static/js/app.js?v=N` (after Chart.js, also `defer`). The only inline script is the one-line theme boot in `<head>` (sets `<html data-theme>` from `localStorage.theme` or the system before first paint, so the page never flashes the wrong theme). `/static` is served by `CachedStatic` in `main.py`: any URL with `?v=` is cached for a year as immutable, so **bump `?v=` in index.html whenever app.js, styles.css or tailwind.css changes** (unversioned images get one day). Responses over 1 KB are gzipped (`GZipMiddleware`; zip/images excluded).

Tailwind is **compiled**, not the CDN: `tailwind.config.js` (theme colors/fonts) scans `templates/index.html` and `static/js/app.js`, and `sh scripts/build_css.sh` (needs Node/npx, Tailwind 3.4.17) writes the minified `static/css/tailwind.css`, which is committed (the VPS needs no Node). After using a Tailwind class that didn't exist anywhere before, rebuild and bump its `?v=`. Never build class names by string concatenation, the scanner wouldn't see them. `styles.css` loads **after** `tailwind.css`, so component rules win ties without `!important`.

Design system (`static/css/styles.css`): dark ("Noite") and light ("Porcelana") themes are CSS variables on `:root[data-theme=…]`. The Tailwind brand colors (`ink`, `panel`, `card`, `neon`, `blush`, `mute`) are `rgb(var(--c-*) / <alpha-value>)` channels, so `bg-card`, `text-mute`, `border-neon/20` switch theme by themselves; `.text-white` is remapped to `var(--fg)`. Never hardcode a color in CSS/JS that must follow the theme: use the tokens (`--fg`, `--muted`, `--line`, `--accent`, `--ok/--warn/--bad`, `--slice-gap`…) and, in JS, `cssVar()`. Glass surfaces are `.glow`, `.kpi-card`, `#pane-dashboard article`, `#cloaker-results`: real `backdrop-filter` only with a fine pointer (desktop); on touch they are near-opaque, and nothing animates behind them (static aurora), because a moving background forces every blur to repaint each frame. Popovers inside the header (bell panel) are near-opaque because a backdrop-filter nested in another one can't see past its parent. Pointer effects (app.js, one rAF-throttled `pointermove` listener): `--mx/--my` drive the laser border (`::before`) and glare (`::after`, both `z-index:-1` inside `isolation:isolate`, so children need no positioning), `.is-lit` turns them on, and `.tilt` + `--rx/--ry` tilt cards matching `TILT_SELECTOR` (never forms; skipped with reduced motion). State rules use `:is(…)` because `#pane-dashboard article` outranks a plain class. On desktop with a mouse, `#sidebar` is fixed and collapsed to icons (4.75rem; `main` gets that margin) and expands over the content on `:hover`/`:focus-within` with staggered labels; without a fine pointer it stays open. Chart legends are circles: `Chart.defaults.plugins.legend.labels.generateLabels` paints each item with `dataset.legendColor` (or the border color). Never put a CSS `filter` on SVG strokes (gauge, sparkline): Chromium paints the whole filter region as a square. Mobile navigation is the fixed `#bottom-nav` (Dashboard, Operações, Coletores, Arquivadas, Mais) plus `#more-sheet` for `MORE_TABS` (post, cloaker, settings); `setTab` marks `.nav-btn`, `.tab-btn` and `.more-item` (the old `#mobile-nav` row is gone). Rules here that set `display` on an element carrying a Tailwind `hidden`/`md:hidden` must respect it themselves (styles.css wins ties). `index.html` ships skeleton placeholders (`.skel`, `.chart-skel`) inside the dashboard containers; the first render replaces them. `toast(message, kind)` shows an icon and a countdown bar; without `kind` it guesses ok/error/shield/info from the text. KPI numbers use `countTo` (animates from the value on screen). UI copy uses sentence case ("Atualizar dados", "Melhor conta"); tracked uppercase is reserved for the "Monitoramento Real" tagline. The theme button toggles with a circular View Transition from the button (`.theme-switching` disables transitions meanwhile) and `applyChartTheme()` recolors Chart.js. Chart.js comes from jsDelivr; Cropper.js is loaded on demand (`loadCropper`) only when a profile photo is picked. Logo is `static/img/logo-256.webp`.

Speed: the dashboard keeps every period it has seen in memory (`dashCache`) and renders it on click while the fresh one loads; after the first load it prefetches the other periods when the browser is idle; "today" without folder is saved in `localStorage["dash_snapshot"]` (cleared on logout) so a logged-in open paints immediately while `/api/config`, `/api/me` and `/api/dashboard` run in parallel. The auth modal starts hidden (`off`) and boot shows it when there is no token. Health/alerts/bell side loads run at most every 30 s, not on every period click. Cards don't use `backdrop-filter` (only `aside`/`header`/modals do): with the animated orbs behind, it repainted every card each frame. The login token is kept in `localStorage["access_token"]` and sent as a Bearer header by the `api()` helper.
